# Portable IssueOps bootstrap and adoption

Status: completed.

Decision: **Adopt**.

## Original documented intent

The initiative was approved through [planning issue #115](https://github.com/8ft0-ai/IssueOps/issues/115), formalised by [PR #116](https://github.com/8ft0-ai/IssueOps/pull/116) and governed for delivery by parent issue [#117](https://github.com/8ft0-ai/IssueOps/issues/117).

The exact approved roadmap before delivery and close-out is preserved at merge commit [`18c9bd6b37b4eb9219f3a5344a3bcd255520d54c`](https://github.com/8ft0-ai/IssueOps/blob/18c9bd6b37b4eb9219f3a5344a3bcd255520d54c/planning/roadmap/portable-issueops-bootstrap-and-adoption.md).

The intended outcome was to prove that an unfamiliar or fresh-context agent could begin with a pinned portable IssueOps specification and an existing repository, assess without mutation, preserve local conventions, select the lightest sufficient posture, create one local bootstrap issue as the first write, deliver the bootstrap through local controls, deliver one subsequent genuine issue and support an evidence-based `Adopt`, `Adapt` or `Reject` decision.

The source identity used by the formal pilot was:

- specification: `IssueOps Bootstrap 0.1`;
- pinned entry point: [`BOOTSTRAP.md` at `fb2c42b1767d2baced01ee0539264bb80268beeb`](https://github.com/8ft0-ai/IssueOps/blob/fb2c42b1767d2baced01ee0539264bb80268beeb/BOOTSTRAP.md); and
- exact external authority: [issue #121 comment `5138524528`](https://github.com/8ft0-ai/IssueOps/issues/121#issuecomment-5138524528).

## Retrospective interpretation

Not applicable. The initiative used a contemporaneous approved roadmap, separately delivered source pack and documentation, and an explicitly authorised fresh independent-agent pilot. This record describes actual delivery without rewriting later findings as original plans.

The earlier candidate `8ft0-ai/decision-register` was withdrawn before the formal Level 3 pilot because it had already adopted IssueOps and could no longer provide a clean pre-adoption baseline. Its prior work remains observational evidence only. The formal pilot used `8ft0-ai/mri-fourier-lab` from verified commit `4cd7dda2630a1d8da4c7bc69c77e26050a71d648`.

The initiative delivered the complete portable adoption path:

- `AGENTS.md`;
- `.github/ISSUE_TEMPLATE/change.md`; and

### Evidence level

The bootstrap path and subsequent genuine issue are classified as **Level 3 — fresh independent-agent walkthrough**.

The execution began from the pinned bootstrap source, exact target repository, authority record and normal authenticated repository access. Each target merge required a separate human decision.

## Intended versus actual delivery

The approved four-slice delivery model was retained:

1. source contract and ownership;
2. external entry point and adaptable source pack;
3. human and normative adoption guidance; and
4. external pilot, comparative proof and close-out.

Actual delivery matched the intended capability and authority boundary. Material differences and decisions were:

- the initially considered `decision-register` target was withdrawn before the formal pilot because it no longer had a fresh pre-adoption state;
- `mri-fourier-lab` was separately authorised with an immutable baseline and per-PR human approval;
- minimal adoption required three target-local surfaces rather than copying canonical IssueOps documentation;
- no stage machinery, labels, workflow, installer, generator or schema was installed in the target;
- the subsequent issue was an accessibility improvement selected only after bootstrap merge verification;
- target validation used source/diff evidence because the target had no PR-triggered checks;
- browser validation used an exact-content in-memory Chromium path because local origins were blocked; and
- public Pages observation remained unavailable rather than being claimed from an unobservable push-to-`main` workflow.

No unsupported application change occurred during bootstrap. No target settings, permissions, branch protection, required checks, auto-merge, dependencies, build tooling or publication configuration changed.

## Observed limitations and friction

- The target repository had no PR-triggered CI or commit statuses. Validation was therefore source-, syntax- and browser-based.
- The connected workflow lookup exposes pull-request runs but not the target's push-to-`main` Pages run. The published surface could not be reached from the execution or search environment.
- The execution container could not resolve GitHub; authoritative repository work used the authenticated connector.
- Browser administrator policy blocked local HTTP and `file:` origins.
- External MathJax could not be loaded during browser checks and was stubbed without changing application integration.
- Connector contents operations produced one narrow commit per file rather than one consolidated implementation commit.
- A test assertion initially used rendered `innerText` inside a closed `<details>` element; it was corrected to inspect `textContent`. No application remediation was required.
- Two attempted `main` to `main` PR creations used the wrong connector action and were rejected with `422`, creating no repository object.
- Later reaction tool-selection misses briefly changed target PR reaction state. All reactions were removed and both target PRs were fetched with empty reaction sets.

The reaction events were recorded as a contained **minor execution deviation**. No issue, branch, commit, file, review, approval, check, merge or publication evidence became stale. The corrective control for close-out is a named, schema-verified action check immediately before every mutation.

These limitations and wrong turns affected execution ergonomics and the strength of publication evidence, but not the proof of first-write discipline, posture proportionality, local lifecycle adoption, source correctness, human merge authority or subsequent real-use delivery.

## Boundaries preserved

The initiative preserved:

- read-only assessment before the first local issue;
- the local issue as the first target-repository write;
- target-repository authority over every later mutation;
- readiness and a detailed implementation plan before each branch;
- one issue-scoped branch per target issue;
- explicit safe-operation checks and deviation disclosure;
- final-head validation and honest completed, pending and unavailable evidence states;
- pull requests as the review evidence pack;
- groundedness review that checks fulfilment and scope control;
- separate independent human approval and merge decisions;
- no auto-merge or delegated target merge authority;
- no unsupported workflow, settings, permission, branch-protection or required-check mutation;
- no bootstrap application, Fourier, MRI, asset, dependency or publication change;
- no stage machinery as the default posture; and
- no dependency on issue #90 or the modular-session initiative for correctness.

## Decisions and lessons

Decision: **Adopt** the portable IssueOps bootstrap and adoption pack.

The evidence supports adoption because a fresh agent could:

- start from the pinned source and exact local authority;
- assess an unfamiliar repository without mutation;
- preserve the target's runtime and publication conventions;
- choose the lightest sufficient posture;
- create the correct first local issue;
- deliver a bounded bootstrap through readiness, planning, branch, validation, PR evidence and human review;
- use the adopted lifecycle for a real source-backed issue; and
- retain reproducible evidence without authority expansion.

No defect in the specification required `Adapt`, and no safety, proportionality or portability failure supports `Reject`.

Lessons:

- capability mapping is more portable than requiring canonical filenames;
- the first-local-issue rule creates a strong, observable authority handoff;
- minimal adoption can remain small while still making the complete manual lifecycle discoverable;
- source identity and target authority should be immutable in the local issue and PR;
- publication evidence must remain explicitly unavailable when the execution environment cannot observe it;
- agent groundedness and human approval are complementary but not interchangeable;
- exact action-schema verification is an important operational control when several connector actions have similar names; and
- one subsequent genuine issue is materially stronger evidence than a synthetic bootstrap-only walkthrough.

## Implications for the next stage

The portable manual bootstrap is now a proven input to later adoption and modular-session work. The current mutable entry point may be recommended while each real adoption continues to record a pinned commit identity.

Later work may consider:

- a thinner invocation or session launcher that supplies the pinned source, target and authority without copying the protocol;
- reusable close-out evidence formatting;
- better publication-surface discovery or explicit fallback guidance; and
- stronger tool-action selection controls.

Those are later planning questions, not defects that block adoption. They must not weaken the local execution-contract handoff, proportionate posture selection, evidence honesty or human merge authority.

Issue [#113](https://github.com/8ft0-ai/IssueOps/issues/113) independently governs the approved modular IssueOps session architecture. This **Adopt** decision may inform that initiative, but does not grant implementation authority, lifecycle automation, automatic execution, auto-merge or repository-setting changes.
